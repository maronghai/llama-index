# Framework Architecture and Core Concepts

A large language model knows facts from its training data, but it does not know your private company handbook, your customer tickets, or your product inventory. If you want the model to answer questions about these private sources, you must feed relevant excerpts into the prompt as context. This architecture is retrieval-augmented generation (RAG).

LlamaIndex is an orchestration framework built specifically for this workflow. It handles the path from raw files on disk to context-augmented answers.

## The Five Stages of RAG

Every retrieval system built with LlamaIndex moves data through five distinct stages:

- Loading: Read unstructured files¡ªPDFs, text files, database records, API outputs¡ªand convert them into standardized container objects.
- Indexing: Split those containers into smaller pieces, compute mathematical representations called embeddings, and organize them into searchable data structures.
- Storing: Persist the index and its pieces so you do not recompute embeddings every time your application boots.
- Querying: Take a user question, find the most relevant pieces, send both the question and the pieces to the model, and receive a formulated answer.
- Evaluation: Measure whether the retrieved pieces were relevant and whether the model answered truthfully.


```
Raw Data (PDF, SQL, API) --- 1. Loading --> Documents --- 2. Indexing --> +Index --- 3. Storing --> Vector Store
User Query --- 4. Querying --> Vector Store
Vector Store --- Retrived Nodes --> Response Synthesizer --- Answer --> User
```

## Documents and Nodes

LlamaIndex standardizes data using two primary data abstractions: Document and Node.

A Document represents an entire source record. It might be an entire 20-page PDF, an entire web page, or one row from a database table. A Document contains:

- The text content.
- A dictionary of metadata (such as file_name, page_label, or created_at).
- A unique identifier string (doc_id).

A Node represents a atomic chunk of a Document. A language model cannot read an entire 500-page manual in one query prompt because of context window limitations and latency costs. You must split each Document into smaller pieces. In LlamaIndex, those pieces are Node objects.

Each Node keeps a reference to its parent Document. A Node also inherits the metadata of its parent Document, and can hold its own specific metadata, such as its position in the document.

```python
from llama_index.core.schema import Document, TextNode

# A Document represents the whole file
doc = Document(
    text="Acme Corp refund policy: Full refunds within 30 days. Contact support@acme.test.",
    metadata={"category": "billing", "source": "terms.txt"},
)

# A Node represents a chunk derived from a Document
node = TextNode(
    text="Acme Corp refund policy: Full refunds within 30 days.",
    metadata={"category": "billing", "source": "terms.txt", "chunk_index": 0},
)
node.relationships[node.relationships.keys()]  # Tracks parent Document ID
```

The relationship link is critical. When a `Node` matches a query, your application knows exactly which file, section, or database record produced that snippet.

### The Global Settings Object

LlamaIndex uses a central configuration singleton named Settings. Before version 0.10.0, configuration lived in a bundle called ServiceContext. Modern LlamaIndex applications use Settings directly.

Settings controls which components execute across your pipeline when you do not specify them by hand:

- Settings.llm: The language model that generates responses (defaults to OpenAI gpt-3.5-turbo or gpt-4o if your API key is present).
- Settings.embed_model: The model that converts text into high-dimensional vectors (defaults to OpenAI text-embedding-ada-002 or text-embedding-3-small).
- Settings.chunk_size: The token count limit for each generated Node (default is 1024).
- Settings.chunk_overlap: The number of tokens shared between adjacent chunks to preserve continuity (default is 20).

```python
from llama_index.core import Settings
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding

# Explicitly configure framework defaults
Settings.llm = OpenAI(model="gpt-4o", temperature=0.1)
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")
Settings.chunk_size = 512
Settings.chunk_overlap = 50
```

REMEMBER> Change Settings.chunk_size before you create an index. Modifying Settings.chunk_size after an index is created will not re-chunk data that is already stored.

### Building an End-to-End Pipeline

To understand how these components interact, follow a minimal pipeline that indexes text and answers a user question.

```python
from llama_index.core import VectorStoreIndex, Document

# 1. Loading: Create Document objects
docs = [
    Document(
        text="The team lunch is every Friday at 12:30 PM in Cafeteria B.",
        metadata={"topic": "office_rules"},
    ),
    Document(
        text="The engineering standup runs Monday through Thursday at 9:30 AM via Zoom.",
        metadata={"topic": "meetings"},
    ),
]

# 2. Indexing: Build an in-memory vector index
index = VectorStoreIndex.from_documents(docs)

# 3. Querying: Create an engine and run a search
query_engine = index.as_query_engine()
response = query_engine.query("When is the engineering standup?")

print(str(response))
```

```text
The engineering standup is held Monday through Thursday at 9:30 AM via Zoom.
```

Let us inspect what happens under the surface during this script:

- VectorStoreIndex.from_documents(docs) reads the documents.
- It invokes a default node parser using Settings.chunk_size to split the text into Node objects.
- It passes each Node text to Settings.embed_model to generate an array of floating-point numbers.
- It stores both the text and the vectors in an in-memory storage context.
- index.as_query_engine() constructs a query pipeline.
- When query() runs, the engine embeds the user question, finds the nearest nodes by mathematical cosine distance, and packs those nodes into a system prompt for Settings.llm.

Inspecting Response Objects
The object returned by query_engine.query() is not a plain string. It is a Response container that wraps both the output text and the evidence used to form it.

When an LLM produces an incorrect answer, you need to know if the model hallucinated or if the retrieval step fetched the wrong text chunks. The Response object allows you to audit the retrieval directly:

```python
# response is the object returned by query_engine.query(...)
print("Synthesized text:")
print(response.response)

print("\nRetrieved source nodes:")
for source in response.source_nodes:
    print(f"- Score: {source.score:.4f}")
    print(f"  Content: {source.node.get_content()}")
    print(f"  Metadata: {source.node.metadata}")
```

```
Synthesized text:
The engineering standup is held Monday through Thursday at 9:30 AM via Zoom.

Retrieved source nodes:
- Score: 0.8712
  Content: The engineering standup runs Monday through Thursday at 9:30 AM via Zoom.
  Metadata: {'topic': 'meetings'}
```

Each item inside response.source_nodes is a NodeWithScore object. It provides:

- node: The underlying TextNode containing the chunk text and metadata.
- score: The similarity score computed between the query embedding and the node embedding (higher usually indicates closer semantic match).

TIP> If your model generates irrelevant answers, check response.source_nodes first. If the source nodes lack the necessary information, your parsing or retrieval strategy is at fault, not the LLM.
